# Shipping MARU to the Play Store

Android only for now. `android/` and `ios/` are generated by `expo prebuild` and are
gitignored, so **every native setting lives in `app.json`** — never edit the generated
project by hand, it will not survive the next build.

## 1. One-time setup

### AniList OAuth client

Sign-in is dead without this. Create a client at <https://anilist.co/settings/developer>:

| Field | Value |
|---|---|
| Name | MARU |
| Redirect URL | `maru://auth` (exactly — AniList matches it verbatim) |

`maru://auth` is what `makeRedirectUri({ scheme: 'maru', path: 'auth' })` resolves to in a
development build or a store build, and it matches the `maru` scheme in `app.json` and the
intent filter in the generated manifest.

> **Sign-in cannot be tested in Expo Go.** There, the same call resolves to
> `exp://127.0.0.1:8081/--/auth`, which is not the URL registered on the AniList client, so
> the flow will always fail. Use `npx expo run:android` or an EAS `development` build.

### Use the client id, not the client secret

AniList issues both. MARU uses only the **id**, and the secret must never be added to this
repo or the app.

AniList supports two grants: the authorization code grant, whose token exchange *requires*
`client_secret`, and the implicit grant, which needs only `client_id`. There is no PKCE, so
there is no way to run the code grant as a public client. Anything shipped in an APK is
extractable, so embedding the secret would leak it to every installer while buying nothing —
the implicit grant is the flow AniList documents for mobile clients, and it is what
`src/state/auth.tsx` implements.

The tradeoff is deliberate: implicit tokens last a year and cannot be refreshed, so an
expired token sends the user back to sign-in. That is handled at launch rather than papered
over. Moving to the code grant would mean standing up a backend to hold the secret and
perform the exchange — out of scope, and not worth it for a client with no server.

If the secret has been pasted into a config file, a commit or a chat, rotate it at
<https://anilist.co/settings/developer>.

Then put the numeric id in `.env` (copy `.env.example`), which `app.config.js` folds into
`expo.extra.anilistClientId`:

```sh
cp .env.example .env
# ANILIST_CLIENT_ID=12345
```

The id is not a secret — it ships inside the APK regardless — but **keep it out of the
repository**, because the repository is public. A client id committed to a public repo gets
copied into other people's builds, and their sign-in traffic is then attributed to this
client for AniList's rate limiting. That is a nuisance, not a breach, and it is trivially
avoided.

So: `.env` locally, and an EAS environment variable for cloud builds.

```sh
npx eas env:create --name ANILIST_CLIENT_ID --value 12345 --environment production
```

Leave `expo.extra.anilistClientId` absent from `app.json`; `app.config.js` fills it from the
environment at build time. A build with no id still succeeds — it ships guest-only, and the
sign-in screen says so — so check the value resolved before shipping:

```sh
npx expo config --type public --json | grep -o '"anilistClientId":"[^"]*"'
```

Verify before building: launch the app, tap **Continue with AniList**, and confirm you land
back in MARU signed in. If the browser tab closes with no session, the redirect URL on the
AniList client does not match `maru://auth`.

### EAS

```sh
npm i -g eas-cli
npx eas login
npx eas init          # links the project, writes expo.extra.eas.projectId
```

### Signing key

Let EAS generate and hold the upload keystore — it is the only sane option here, because the
generated `android/` project is thrown away on every build and its `release` block is wired
to the *debug* keystore, which Play rejects.

```sh
npx eas credentials -p android      # → Keystore → Set up a new keystore
```

Back it up (`eas credentials` → Download) and enable Play App Signing in the Console.

### Play Console

Create the app under package name **`app.maru.tracker`**. This must match `expo.android.package`
and can never be changed after the first upload.

## 2. Build and submit

```sh
npx eas build -p android --profile preview      # installable APK for device testing
npx eas build -p android --profile production   # AAB for Play
npx eas submit -p android --latest              # uploads to the internal track as a draft
```

`production` uses `appVersionSource: "remote"` with `autoIncrement`, so EAS owns
`versionCode` — bump `expo.version` in `app.json` by hand for user-visible releases, and
leave `versionCode` alone.

> **Unverified:** release builds now run R8 (`enableProguardInReleaseBuilds`) and resource
> shrinking. This could not be compiled locally — no Java runtime on the dev machine — so the
> first production build is the real test. If it fails or the app crashes on launch only in
> release, add keep rules to `android/app/proguard-rules.pro` via the
> `expo-build-properties` plugin's `extraProguardRules`, or set both flags back to `false`
> in `app.json` to unblock the release.

## 3. Play Console questionnaires

### Privacy policy

Required. Host `PRIVACY.md` somewhere public (GitHub Pages, a gist, any static host) and
paste the URL into **App content → Privacy policy**. The same text also ships in-app at
Settings → Session → Privacy policy, which is what reviewers usually look for.

### Data safety

MARU has no backend, analytics, ads or crash reporting. Recommended answers — **review these
yourself before submitting**, you are the one signing the declaration:

- Does your app collect or share any of the required user data types? — **No**
- Is all user data encrypted in transit? — **Yes** (HTTPS to `graphql.anilist.co` only;
  cleartext traffic is disabled at the manifest level)
- Do you provide a way for users to request data deletion? — **Yes**, in-app sign-out plus
  <https://anilist.co/settings/apps> to revoke the token

Rationale for "no collection": the AniList token and preferences never leave the device, and
list edits go to *the user's own AniList account* at their direction. Nothing is collected by
the developer. Google treats a third-party API the user authenticates to themselves as out of
scope for collection.

### Account deletion

Play requires an account-deletion path only for apps that create accounts. MARU creates none —
it authenticates against an existing AniList account. Point the deletion URL at
<https://anilist.co/settings/account> and note in the review comments that MARU is a
third-party client holding no accounts of its own.

### Content rating

Answer the IARC questionnaire honestly. MARU surfaces the AniList catalogue, which includes
mature titles; adult content is off by default and gated on the user's AniList account
settings. Expect **Teen / PEGI 12** or higher.

### Ads and target audience

No ads. Target audience 13+ — do **not** opt into the Families programme.

## 4. Store listing

App name **MARU**, 30 chars max. You still need to produce:

- Feature graphic, 1024 × 500 PNG
- At least 2 phone screenshots (4 – 8 recommended), 16:9 or 9:16, min 320px
- Short description, 80 chars
- Full description, 4000 chars

Suggested copy:

> **Short:** Track every anime you watch, in one calm place.
>
> **Full:** MARU is a fast, quiet client for your AniList library. Pick up where you left off
> with a continue-watching rail that knows what aired today, mark episodes with a single tap,
> and keep scores and progress in sync across every device signed in to your AniList account.
> Browse trending and seasonal titles without an account at all.
>
> MARU is an independent, open-source client. It has no servers, no analytics and no ads —
> your token and preferences never leave your device.
>
> Not affiliated with or endorsed by AniList.

## 5. Pre-submission checklist

- [ ] `ANILIST_CLIENT_ID` set, sign-in verified end-to-end on a real device
- [ ] Sign out → sign back in works; token survives an app restart
- [ ] Guest mode hides every tracking affordance
- [ ] Production AAB builds with R8 enabled and launches without crashing
- [ ] Privacy policy URL live and reachable
- [ ] Data safety, content rating and target-audience forms submitted
- [ ] Internal testing track release installed and smoke-tested before promoting

## 6. Rolling out an update

### Version numbers

Two numbers, and they do different jobs:

| | Where | Who bumps it |
|---|---|---|
| `versionName` — what users see, e.g. `1.1.0` | `expo.version` in `app.json` | **You**, by hand |
| `versionCode` — the integer Play orders builds by | managed remotely by EAS | **EAS**, via `autoIncrement` |

`eas.json` sets `appVersionSource: "remote"`, so EAS holds the `versionCode` counter and
increments it on every production build. Do not set it in `app.json` — it will be ignored and
will drift out of sync with what Play has seen.

Play permanently rejects a `versionCode` it has already accepted, even from a deleted draft.
If a build is burned, the next one just takes the next number; nothing to fix.

### The loop

```sh
# 1. bump the user-visible version in app.json → expo.version
# 2. sanity check
npm run typecheck
# 3. build the AAB (EAS increments versionCode)
npm run build:production
# 4. upload to the internal track as a draft
npm run submit
```

Then in the Play Console: **Release → Internal testing → Edit release**, write the "What's
new" notes, and roll out. Install it on a real device from the internal-testing opt-in link
and smoke-test before going further.

### Promoting through tracks

```
internal  →  closed (alpha/beta)  →  open  →  production
```

Internal reaches up to 100 named testers and goes live in minutes with no review wait — it is
the only fast feedback loop you have, so always land there first. Promote with
**Release → the track → Promote release → select the next track**; the same artifact moves
forward, so nothing is rebuilt and the `versionCode` stays put.

Never submit straight to production. `eas.json` deliberately pins
`track: internal, releaseStatus: draft` so a stray `npm run submit` cannot reach users.

### Staged rollout, and why there is no undo

Production releases take a rollout percentage — start around 10–20%. Watch **Quality →
Android vitals** for crash rate and ANRs for a day, then raise it (20 → 50 → 100).

If something is wrong, **Halt rollout** stops *new* users receiving the build. It does **not**
revert anyone who already updated. Play has no rollback — the only remedy is to ship a fixed
build with a higher `versionCode`. This is the reason for the internal-track step and the
staged percentage; both are cheap, and the alternative is not.

### Release notes

"What's new" is per-language, 500 characters, and set per release. Reusing the previous
release's notes is a common way to ship a confusing changelog — write them at step 4.

### Review times

Updates to an existing app are typically hours to a couple of days. The very first submission
of a new app takes materially longer. Policy-sensitive changes (permissions, data safety
answers) can trigger a longer look.

### JS-only changes still need a full release

`expo-updates` is not installed and OTA updates are off, so there is no way to push a JS fix
without a store round-trip. If that becomes painful, adding
[EAS Update](https://docs.expo.dev/eas-update/introduction/) lets JS and asset changes ship
in minutes while native changes continue to go through Play. It needs `expo-updates`
installed, `channel` fields restored to the `eas.json` build profiles, and a `runtimeVersion`
policy — note that Play's policy still requires that OTA updates not materially change what
the app does.

### First release only

A newly created **personal** developer account has to run a closed test with a minimum number
of testers for a continuous period before it can apply for production access — this was 12
testers for 14 days, but Google has changed the thresholds more than once. Confirm the
current rule in the Console under **Dashboard → production access** before planning the
launch date, because it sets your earliest possible ship date and cannot be shortcut.
Organisation accounts are exempt.
